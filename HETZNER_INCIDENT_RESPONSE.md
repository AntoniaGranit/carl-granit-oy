# Email to Hetzner - Incident Response

**Subject:** Response to Abuse Notification - DDoS Detection (IP: 157.180.47.239)

---

Dear Hetzner Abuse Team,

We received your notification regarding suspected abuse from our server (IP: 157.180.47.239) on December 6, 2025, specifically concerning UDP packets to port 53 (DNS) detected between 10:34:08 and 10:34:09.

## Incident Summary

Upon investigation, we discovered that one of our Docker containers had been compromised with malware. The excessive DNS queries were a symptom of this compromise - the malware was attempting to communicate with command-and-control servers, which triggered the DDoS detection system.

## Root Cause Analysis

Our investigation revealed:

1. **Compromised Container**: A Docker container running a Next.js application was infected with malicious binaries (`linux_amd64`) and scripts
2. **Malware Activity**: The malware was attempting to download additional payloads from suspicious IP addresses (103.135.101.15, 194.69.203.32)
3. **DNS Queries**: The excessive DNS queries to 23.176.168.11 were generated by the malware attempting to resolve C2 server domains
4. **Attack Vector**: The malware was likely injected at runtime, possibly through a vulnerable dependency or application vulnerability

## Immediate Actions Taken

Upon discovery, we immediately:

1. **Stopped the Compromised Container**: Immediately halted and removed the infected container to prevent further malicious activity
2. **Isolated the System**: Verified no other containers or services were affected
3. **Cleaned the Environment**: Removed all malicious files and processes from the server

## Security Measures Implemented

To prevent future incidents, we have implemented comprehensive security hardening:

### 1. Docker Container Security
- **Non-Root Execution**: Containers now run as unprivileged user (UID 1001) instead of root
- **Read-Only Filesystem**: Root filesystem is read-only, preventing malware from writing persistent files
- **Capability Dropping**: Removed all unnecessary Linux capabilities, only allowing minimal required permissions
- **Resource Limits**: Implemented CPU and memory limits to prevent resource exhaustion attacks
- **Security Options**: Enabled `no-new-privileges` to prevent privilege escalation

### 2. DNS Configuration
- **Explicit DNS Servers**: Configured containers to use reliable public DNS servers (8.8.8.8, 1.1.1.1) instead of the host resolver
- **DNS Search Disabled**: Removed DNS search domains to reduce unnecessary queries

### 3. Dependency Security
- **Version Synchronization**: Fixed version mismatches between package.json and lock files
- **Dependency Audit**: Conducted comprehensive audit of all dependencies
- **Regular Updates**: Established process for regular dependency updates and security audits

### 4. Build Process Security
- **Multi-Stage Builds**: Implemented multi-stage Docker builds to reduce attack surface
- **Minimal Base Images**: Using minimal Alpine Linux base images
- **Build Tool Removal**: Removed unnecessary build tools from production images

### 5. Monitoring and Detection
- **Health Checks**: Implemented container health monitoring
- **Log Monitoring**: Enhanced logging and monitoring for suspicious activity
- **Resource Monitoring**: Added resource usage monitoring to detect anomalies

## Current Status

- ✅ Compromised container has been removed
- ✅ All malicious processes have been terminated
- ✅ Security hardening measures have been implemented
- ✅ New secure container configuration is ready for deployment
- ✅ No further suspicious network activity detected

## Prevention Measures Going Forward

We have established the following ongoing security practices:

1. **Regular Security Audits**: Weekly dependency audits and vulnerability scans

3. **Monitoring**: Continuous monitoring of network traffic and container behavior
4. **Incident Response Plan**: Documented procedures for responding to security incidents
5. **Security Documentation**: Comprehensive security hardening documentation for the team
